How it works

Input is validated against a github.com allowlist, so the scanner can't be pointed at internal addresses. Secrets are found by provider-shaped patterns, plus an entropy check on generic ones, and redacted before display. Dependencies from 12 manifest formats are checked against OSV.dev for known vulnerabilities and for packages flagged as outright malicious. Thirteen hygiene rules cover things like committed .env files and missing CI. Claude writes the score and explanation.

Pipeline stages, in order:

  1. Validate URL
  2. Walk the tree
  3. Find secrets
  4. Check dependencies
  5. Check hygiene
  6. Score

What it guards against

The model not being there. A missing key, a rate limit, a network error or an API error all fall back to a deterministic scoring engine, so a scan still returns a score. On the test fixtures that engine gives a clean repository 99.2 (A) and one with a leaked AWS key and a malicious package 50.2 (F). One known gap: if OSV.dev is down entirely, dependencies currently score as clean when they should score as unknown.

How I know it works

12 offline tests, all passing with no API keys set.
